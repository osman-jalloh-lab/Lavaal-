## Consent, storage and delivery

Browser session, review and confirm require configured trusted Origin entries, cookie binding and CSRF. Host supplied by a client is not a trusted-origin source. The separately authenticated vendor tool may draft only; it receives no browser proof and cannot mint/redeem consent. Full review includes provided and skipped fields; only review issues the short-lived digest-bound token. Edits invalidate earlier consent. Browser Send atomically consumes consent; model text or confirmed:true never authorizes sending.

The storage adapter exposes serialized `transaction(Map => ...)` operations. Its only A1 implementation is a shared test mock, not durable serverless storage. Production rejects mock, no production provider is installed, and no existing ops store or `lavaall-ops-v2` is accessed. Independent simulated handlers share atomic counters and confirmation state.

Session/draft and minimal result lifetime: 30 minutes. Consent: 2 minutes. IP limits: 3 new sessions/hour and 6/day; window buckets expire at UTC boundary. Global submissions: 20/day, turns: 10/session. Raw IP is not retained; an HMAC with server salt identifies quota buckets. Expired draft data becomes unavailable and cannot initiate another delivery. A real adapter must implement expiration/deletion, minimal retained digests and counters, and deletion support before activation. Monthly accounting retains only aggregate cost/reservation data, no inquiry text or contact details.

Confirmation records an uncertain state before I/O, with a stable idempotency key. Concurrent clicks/retries return stable state without a second attempt. Acknowledgement requires HTTP success AND JSON ok:true. Failure, timeout, interruption, or a crash may follow delivery, so the response is uncertain and there is no automatic retry. This is at most one application attempt, not a guarantee of exactly-once mail delivery by an external provider. After record expiry the old draft cannot be retried.

Chat uses the existing CONTACT_WEBHOOK_URL / CONTACT_WEBHOOK_SECRET transport contract, server-controlled support@lavaall.com only, the `[Lavaall Website` subject family, original contact-form opening convention, and `Channel: website chat`. No arbitrary recipient or webhook is accepted. Phone-only Apps Script omits replyTo; public contact validation and router allowlists must not be weakened. No real transport is installed in A1.

## Review and local test contract

`api/chat-inquiry.js` exports an always-disabled Vercel handler. Its `createHandler` factory accepts only an explicitly enabled `runtime: 'test'` mock store plus injected transport. There is no environment setting that activates the real widget or outbound delivery in A1. The local browser stub requires loopback, exact `/`, and an injected `window.LAVAALL_ASSISTANT_LOCAL_TEST` transport; no vendor script is downloaded. The inert homepage script is the only mount entry.

Mock HTTP contract: POST `/api/chat-inquiry?action=session|draft|review|confirm|turn`, JSON only, maximum 8192 bytes. Session returns sessionId and CSRF; the random browser proof stays in an HttpOnly SameSite=Strict cookie, Secure unless explicit local tests. Draft requires server-only Bearer authentication and `{sessionId, fields, eventId}`. It returns only draftId. Browser review requires `{sessionId, csrf, draftId}` and returns summary, skipped fields, token and stable idempotencyKey. Confirm requires those browser bindings and `{draftId, token, idempotencyKey}`. Turn reservation is test-server configured, not a vendor-supplied cost. The UI's injected local transport must orchestrate synthetic session/draft setup; it is not a deployable vendor adapter.

The store mock lazily deletes expired records during transactions and clones state/returns for rollback and reference isolation. A2 requires actual TTL deletion and a durable transactional adapter with those semantics; test memory does not claim persistent storage. Cost reservations are conservatively retained in addition to reported all-in spend, even when a later bill includes them; this can stop usage early and never establishes a true vendor cap. No automatic refund or spend reconciliation is implemented. The provider draft event id is replay-deduplicated within the session lifetime; no general provider billing-event endpoint is exposed.

The only Apps Script change is conditional inclusion of replyTo for phone-only inquiries. It preserves recipient allowlists and contact-form opening text. It is source code only: no Apps Script deployment was updated. Public `api/contact.js` is byte-for-byte unchanged, including its existing baseline weaknesses pending #75. No dependency branch was modified.

Reviewable files: `api/chat-inquiry.js`, `api/_chat/{service,store,contact}.js`, `assets/js/customer-assistant.js`, homepage inert script tag, privacy draft, conditional router replyTo, this documentation/config/KB/policy, and scoped mocked tests/safe suite harness. The non-loaded `docs/customer-assistant/env.example` contains default-off flags and blank future adapter names for review only; it does not configure an environment or activate A1.

Concurrent confirmations briefly wait for the first attempt's persisted result (up to 100ms in this scaffold). If the attempt stalls, confirmation freezes the result as uncertain; a late acknowledgement cannot change that terminal result or cause a retry. A2 must replace this bounded test polling with a reviewed durable completion/reconciliation mechanism.
